Building a Production-Ready 3-Tier Application on AWS: A Complete Infrastructure Journey

How I deployed a highly available Book Review application using Terraform, Next.js, and AWS, and what I learned debugging every layer of the stack.

F

Florence

Cloud Engineering · AWS · DevOps

Introduction

“It should just work,” I thought, as I typed terraform apply for what I believed would be the final time. Fifteen hours and countless SSH sessions later, I finally understood the difference between making something work and making something production-ready.

This is the story of deploying a three-tier web application on AWS using Infrastructure as Code. The journey took me through VPC networking, load balancers, database connectivity, and the surprising complexity of configuring Next.js environment variables for production.

In this article, I cover:

  • Designing a three-tier architecture on AWS.
  • Provisioning infrastructure with Terraform.
  • Configuring EC2 instances, load balancers, and Amazon RDS.
  • Debugging application, networking, and database problems.
  • Applying lessons about security, availability, and cost.

2. Why use a three-tier architecture?

Separation of concerns

  • Presentation tier: Displays the user interface.
  • Application tier: Processes requests and implements business logic.
  • Database tier: Stores and retrieves application data.

This separation makes it possible to scale components independently, apply different security policies, and troubleshoot problems within a specific layer.

Security through isolation

The web tier receives external traffic through the public load balancer. The application tier is placed in private subnets, and the database is not publicly accessible. Security groups restrict communication between tiers.

Each tier should accept only the traffic it needs. For example, the database should accept MySQL connections from the authorized application tier rather than from the entire internet.

Scalability and performance

Load balancing helps distribute requests between healthy targets. Additional capacity can be introduced when needed, while the frontend and backend can be scaled according to their individual requirements.

3. Infrastructure design with Terraform

Manually creating cloud resources through a console can become difficult to reproduce and maintain. Infrastructure as Code allows resource definitions to be stored, reviewed, version-controlled, and reused.

My Terraform project organized infrastructure configuration into files for resources, variables, outputs, and instance initialization scripts. 

book-review-terraform/
├── main.tf
├── variables.tf
├── outputs.tf
├── userdata/
│   ├── frontend.sh
│   └── backend.sh
└── README.md

My Terraform workflow

# Initialize providers and modules
terraform init

# Review the proposed infrastructure changes
terraform plan

# Apply changes after reviewing the plan
terraform apply

The plan is an important review step. It helps identify proposed additions, modifications, and deletions before they affect the environment.

Network foundation

The network design used a custom VPC with public subnets for the web tier and private subnets for application and database resources. An Internet Gateway supports internet connectivity for public resources, while a NAT Gateway can provide outbound internet access to private resources when required. 

resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true
  enable_dns_support   = true
}

resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id
}

Subnet ranges, routes, and security rules must be consistent with the actual deployment. NAT Gateways and multi-AZ resources also have cost implications.

4. Security groups and traffic flow

AWS security groups act as stateful virtual firewalls. The goal is to permit only the necessary connections between components.

  • The public load balancer accepts permitted web traffic.
  • The web tier accepts requests from its authorized load balancer.
  • The application tier accepts API traffic from the internal load balancer.
  • The database accepts MySQL connections from the authorized application tier.
# Illustrative example: restrict database access
# to the application security group.

resource "aws_security_group" "db_tier" {
  name   = "book-review-db-tier"
  vpc_id = aws_vpc.main.id

  ingress {
    from_port       = 3306
    to_port         = 3306
    protocol        = "tcp"
    security_groups = [aws_security_group.app_tier.id]
  }
}

This is an illustrative excerpt, not a complete, independently deployable Terraform configuration. Resource references must match the actual project files.

5. Configuring EC2 and application startup

EC2 user data scripts can automate instance initialization. In this project, the intended workflow included installing application dependencies, obtaining the application code, building the frontend, configuring Nginx, and starting processes with PM2.

Automating these steps makes instance creation more repeatable. However, a successful EC2 launch does not necessarily mean the application has finished installing or is ready to receive traffic.

Why the Nginx default page appeared

One early lesson was that infrastructure provisioning and application deployment are separate stages. The load balancer could exist while the application setup was still running or had not completed successfully.

Checking user data logs, Nginx configuration, application process status, and target health helps determine where the problem lies.

6. Debugging the deployment: what went wrong?

Problem 1: The frontend used localhost

The frontend attempted to send API requests to localhost:3001. In a user's browser, localhost refers to the user's own device, not the remote backend EC2 instance.

The production frontend needed to use the intended API path so that Nginx could forward requests through the internal load balancer.

Problem 2: Next.js environment variables

Public Next.js environment variables prefixed with NEXT_PUBLIC_ are generally embedded into browser-side code during the build. Changing the server environment after the build does not automatically change those values in already-built JavaScript. 

# Example: set the public API path before building
export NEXT_PUBLIC_API_URL="/api"

npm run build

The correct value also depends on how the application constructs its API request paths. The base URL and request path must be checked together to avoid duplicate segments such as /api/api/books.

Problem 3: The API path was duplicated

The frontend was combining a base URL containing /api with a request path that already included /api. This created an incorrect endpoint.

The solution was to align the frontend's base URL with the request paths and the Nginx proxy configuration. After a configuration change, the application needed to be rebuilt and tested again.

Problem 4: Browser caching showed the old code

Even after correcting the server-side configuration, the browser continued showing an old error. A hard refresh or a clean Incognito session helped distinguish stale browser content from the current deployment. 

# In Chrome or another Chromium browser:
# Ctrl + Shift + R for a hard refresh

Browser caching was a useful troubleshooting lead, but it is important to verify the actual network request and loaded JavaScript before concluding that caching is the cause.

Problem 5: The backend could not connect to MySQL

The backend encountered a database connection timeout. The database hostname had been configured with the port appended to it, even though the database client expected the hostname and port to be supplied separately. 

# Illustrative environment configuration
DB_HOST=your-rds-endpoint
DB_PORT=3306
DB_NAME=your_database
DB_USER=your_database_user

The actual database password should be supplied securely and must never be published in this file. In a production environment, use a suitable secrets-management approach rather than committing credentials to source control.

I learned to verify the database endpoint, port, security-group rules, network reachability, and backend logs together rather than assuming the database itself was the problem.

Useful diagnostic checks

  • Inspect browser DevTools and the Network tab.
  • Check the load balancer's target health.
  • Inspect Nginx access and error logs.
  • Review application process status and logs.
  • Verify API URLs and environment configuration.
  • Test connectivity to the database endpoint and port.

The key lesson is to isolate the failing layer, verify the evidence, make one focused change, and test again.

8. Production-readiness lessons

Infrastructure as Code

Terraform makes infrastructure definitions reviewable and repeatable. It does not remove the need to review plans, manage state securely, protect data, or test recovery procedures.

Immutable infrastructure

Manually changing a running server can create differences between the deployed environment and its source configuration. Where practical, make the fix in the code or initialization process and replace the affected resource through a controlled deployment.

Health checks

Load balancer health checks help identify targets that should not receive traffic. Their paths, timing, and success criteria need to reflect the application. A healthy web process alone may not prove that all downstream dependencies are working.

Multi-AZ architecture

Distributing resources across Availability Zones can reduce the impact of some infrastructure failures. Actual failover depends on the configuration of the load balancers, compute resources, database, and recovery processes.

Secrets management

Database passwords and access credentials should not be hard-coded in application files or exposed in public repositories. Use protected configuration and an appropriate secrets-management service for the environment.

9. Cost optimization considerations

A highly available architecture can cost more than a small development environment. Resources such as NAT Gateways, load balancers, multi-AZ database deployments, and multiple compute instances can contribute to the overall bill.

For development and testing, consider:

  • Removing resources that are no longer needed.
  • Choosing appropriately sized instances.
  • Reviewing NAT Gateway and load balancer costs.
  • Using a simpler topology when high availability is not required.
  • Monitoring actual AWS billing and usage rather than relying only on estimates.

Any change that reduces availability or resilience should be evaluated against the application's requirements. Development cost savings are not automatically suitable for a production workload.

10. What I learned from this project

Technical lessons

  1. Understand build-time configuration. Frontend environment variables may be embedded in the build output.
  2. Check the complete request path. Incorrect routing can make a working backend appear unavailable.
  3. Use logs as evidence. Browser errors, load balancer health, Nginx logs, application logs, and database errors each provide different clues.
  4. Validate network connectivity. Private subnet routing and security groups can prevent connections even when services are running.
  5. Automate repeatable configuration. Infrastructure and startup changes should be captured in the appropriate code and configuration.

Process lessons

  1. Start with a small working deployment before adding complexity.
  2. Document errors, fixes, and important design decisions.
  3. Protect Terraform state and use an appropriate remote backend where required.
  4. Test individual tiers before testing the full application.
  5. Avoid manual changes that cannot be reproduced from the project configuration.

11. What could be improved next?

The architecture provides a foundation for further improvements. These are potential next steps and should not be interpreted as features already deployed.

  • HTTPS: Configure and validate trusted TLS certificates.
  • Auto Scaling: Define scaling policies based on workload and capacity needs.
  • Monitoring: Add alarms for unhealthy targets and important application metrics.
  • Secrets Manager: Store and retrieve sensitive credentials securely.
  • CI/CD: Automate tested build and deployment steps.
  • CloudFront: Evaluate content delivery and caching where appropriate.
  • Database resilience: Review backups, recovery procedures, and read-replica requirements.

Each enhancement should be implemented, validated, and documented according to the needs of the application.

Conclusion

Building this three-tier application taught me that the gap between “it works on my laptop” and “it works reliably in the cloud” is filled with networking, security, configuration, performance, cost, and operational considerations.

The most valuable lesson was learning to troubleshoot methodically. A problem that first appears to be an application bug may turn out to be a routing issue, an environment variable, a stale browser asset, or a database connection setting.

Terraform and other cloud tools help make deployments more repeatable, but reliable results still require careful design, verification, and documentation.

This project strengthened my interest in cloud engineering, Infrastructure as Code, and DevOps. I look forward to building on these skills through more hands-on projects.
